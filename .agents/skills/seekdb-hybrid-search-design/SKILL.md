# seekdb 混合检索方案设计

## 这个 Skill 解决什么问题

seekdb 把向量、全文、标量放进同一个引擎，一条 SQL 就能三路召回。能力越全，选错的机会越多：索引选 HNSW 还是 IVF-PQ、要不要同时建全文索引、过滤条件为什么没走索引、换了 embedding 模型后旧向量怎么办。

本 Skill 给的是**决策流程和判定依据**，不是 API 手册。凡是涉及具体语法的地方，只给能证实的写法；版本敏感的函数名、参数，一律要求查对应版本文档，不许凭记忆拼。

## 何时使用

- 新建检索层：给定数据形态和查询方式，要定表结构、索引类型、召回策略
- 现有检索效果差：语义相近但关键字命中不了（型号、代码标识符、人名）、加了过滤条件 QPS 掉下来
- 要评估一次索引变更：换度量、换量化、调 `ef` 之类的参数，不想拿线上库试

不适用：单纯问"seekdb 怎么安装"、纯 SQL 语法查询（查文档更快）。

## 第 1 步：先把检索需求问清楚

动手前必须确认四项，缺任何一项就先问，不要开始写 SQL：

| 项 | 要问到的具体信息 |
|---|---|
| 数据形态 | 每条记录有没有长文本、有没有结构化字段（时间、作者、分类）、单条多大 |
| 查询方式 | 用户输入是自然语言还是关键词？是否经常出现型号、编号、专有名词 |
| 规模与预算 | 向量条数、维度、内存上限、能否接受磁盘索引的延迟 |
| 一致性要求 | 写入后多久必须可搜到；是否需要事务；是否要多版本并存 |

其中"查询方式"决定要不要上全文：**纯向量检索对精确字符串是天然弱项**。用户如果经常搜 `OB-2024-0117` 这种编号、函数名、错误码，只建向量索引必然漏召回。

## 第 2 步：表结构与 embedding 约定

一条记录通常分成四类列：

- 关系列：主键、时间、作者、分类等，用于过滤和排序
- 向量列：dense 向量存语义；如有需要再存 sparse 向量走关键词权重
- 文本列：原文，供全文索引使用
- JSON 列：可扩展的元数据，避免频繁改表

三条硬约束：

1. **维度与度量在建模阶段一次性定死**。同一列里的向量必须同维度、同模型、同归一化方式。混入不同 embedding 模型的向量，检索结果会静默变差——不报错，只是不准。
2. **换 embedding 模型等于换列**。模型一换，全部向量必须重算，旧向量不能复用。上线前就把"模型版本"记进元数据（如 `embed_model` 列），否则半年后没人说得清这批向量是谁生成的。
3. **归一化策略要和度量匹配**。用内积或余弦时先归一化，用欧氏距离时不要乱归一化。这一步搞反，排序会失真但依然"看起来正常"，最难排查。

建表的具体 DDL（向量类型写法、维度参数、索引创建语句）以 `https://docs.seekdb.ai/` 对应版本文档为准，不要照抄别处的示例。

## 第 3 步：索引选型（内存换精度，磁盘换成本）

seekdb 提供两组向量索引，选择只看一个问题：**内存够不够装下全部向量**。

| 场景 | 建议 | 代价 |
|---|---|---|
| 数据量能全放内存，要求高召回、低延迟 | HNSW | 内存占用最高 |
| 内存紧张但仍要 HNSW 的图结构 | HNSW-SQ（标量量化） | 少量精度损失 |
| 内存极紧、可接受召回再降一点 | HNSW-BQ（二值量化） | 精度损失更明显，需实测 |
| 数据量大、内存装不下 | IVF 系列（含 IVF-PQ） | 需要训练、召回依赖聚类质量、延迟更高 |

配套索引：

- **全文索引**（BM25）：只要查询里可能出现精确词，就建。分词器按语言选，中文别用默认英文分词。
- **标量索引**：出现在 `WHERE` 里的高选择性字段（如 `author_id`、`created_at`）必须有索引，否则过滤会退化成全表扫描。
- **JSON 索引**：元数据查询频繁时建，按实际查询路径建，不要给整个 JSON 建一个大索引。

量化索引上线前必须实测召回率：用一批已知答案的查询跑一遍，和未量化版本对比 top-k 重合度。**不要用"官方说损失很小"代替自己的数据。**

## 第 4 步：单条 SQL 做混合检索

核心思路：把语义召回、关键字召回、结构化过滤放进**同一个执行计划**，让过滤条件下推到存储层，而不是先查回来再在客户端筛。

```sql
SELECT id, title, l2_distance(emb, '[0.12,0.34,...]') AS dist
FROM docs
WHERE MATCH(content) AGAINST('quarterly report')
  AND author_id = 42
  AND created_at > '2026-01-01'
ORDER BY dist APPROXIMATE LIMIT 10;
```

这段来自项目 README，是官方给出的范式。写的时候注意：

- `ORDER BY dist APPROXIMATE` 表示走近似索引；去掉它会退化成精确全扫，数据量大时慢到不可用，但小数据量下它是排查"索引是否生效"的对照手段。
- 距离函数必须和索引度量一致。欧氏距离配余弦索引，结果不会报错，只是排序错。
- 不要写成"向量查 top 100 → 客户端按条件过滤 → 再取 top 10"。这样既浪费召回额度，又会因为过滤掉太多导致结果不足。条件要进 `WHERE`。

**过滤选择性高时**，先用标量条件把候选压到合理规模，再做向量排序，通常比纯向量检索再过滤更稳。

## 第 5 步：要不要重排，用哪种

两路召回的结果怎么合并，三种做法：

| 方式 | 适用 | 注意 |
|---|---|---|
| 加权分数 | 两路分数量纲可比（都归一化过） | 权重需要调，且不同查询最优权重不同，容易过拟合 |
| RRF（倒数排名融合） | 分数量纲不可比、想少调参 | 只看排名不看分数，实现稳，是默认首选 |
| LLM 重排 | 候选少（如 20 条以内）、质量要求高 | 延迟和成本明显上升，不要对全量候选做 |

选择顺序建议：先用 RRF 拿到基线，只有当 RRF 的排序明显不符合业务预期时，再考虑加权或 LLM 重排。**任何重排都必须有离线评测集做对照**，否则无法判断改动是否真的变好。

## 第 6 步：用 FORK 沙箱验证，再 MERGE 回主线

改索引、改度量、调参数这类操作不要直接在生产库上做。seekdb 的 COW 沙箱可以秒级复制整库：

```sql
FORK DATABASE prod_memory TO sandbox_try_ivfpq;
USE sandbox_try_ivfpq;
-- 在沙箱里重建索引、跑评测查询
MERGE TABLE sandbox_try_ivfpq.docs INTO prod_memory.docs STRATEGY THEIRS;
-- 不满意就直接丢弃：
DROP DATABASE sandbox_try_ivfpq;
```

使用要点：

- 沙箱是写时复制，创建几乎不耗存储，可以放心一次开多个做 A/B。
- `MERGE TABLE` 的策略要选对：`THEIRS` 表示以沙箱版本为准。合并前先确认沙箱里的数据是**验证过**的，不要把实验垃圾合回主线。
- 验证完立刻 `DROP DATABASE`，别留一堆忘了名字的沙箱占空间。
- 评测要在沙箱里跑同一批固定查询，记录改动前后的 top-k 重合度与延迟，否则"感觉变好了"不算结论。

## 排查清单（按现象找原因）

| 现象 | 优先怀疑 |
|---|---|
| 搜编号、函数名、错误码搜不到 | 没建全文索引，或分词器把符号切碎了 |
| 加了 `WHERE` 条件后 QPS 断崖下降 | 过滤字段没索引，或过滤没下推，退化成先检索再过滤 |
| 换了模型后结果整体变差但不报错 | 新旧向量混在同一列，维度相同所以没报错 |
| 召回率比预期低很多 | 用了量化索引但没实测；或 `ef` 类参数太小 |
| 同一条数据两次查询排名差异大 | 近似检索本身的抖动，数据量小时改用精确检索对照 |
| 写入后搜不到刚写的数据 | 索引构建是异步的，确认可搜延迟是否符合预期 |

## 硬性要求

1. **不编 API**。函数名、参数名、DDL 语法只写能证实的；不确定就写"以对应版本文档为准"，不要构造看起来合理的函数名。
2. **不编性能数字**。除引用官方基准外，不写"提升 X 倍"这类没有实测支撑的结论。
3. **区分事实与建议**。索引类型的特性是事实；"你的场景应该用 HNSW"是建议，要说明依据（数据量、内存、召回要求）。
4. **参数改动必须给验证方法**。任何调参建议都要附"怎么验证它有效"。
5. 涉及生产库的写操作（建索引、改度量、MERGE）必须先提醒在 FORK 沙箱里做。

## 使用示例

**示例 1：从零设计**

> 用户：我有 200 万条客服工单，想做语义搜索，还要能按产品线和时间过滤，机器 32G 内存。

输出：先确认四要素（维度、是否需要精确词召回、写入频率、可接受延迟）→ 200 万 × 1024 维 float32 约 8GB，加图结构开销后 32G 内存装 HNSW 偏紧 → 建议 HNSW-SQ 或先做维度评估 → 工单里有产品型号和错误码，必须同时建全文索引 → 给出单条混合检索 SQL 骨架（向量 + `MATCH ... AGAINST` + 产品线/时间过滤）→ 用 RRF 合并 → 在沙箱里对比 SQ 前后的 top-20 重合度。

**示例 2：效果排查**

> 用户：搜"OB-2024-0117 这个报错怎么解决"总是搜不到对应工单，但语义相近的能搜到。

输出：判断是纯向量检索对精确字符串的固有弱点 → 检查是否建了全文索引、分词器是否把连字符切散 → 给出"向量 + 全文 + RRF"的组合方案 → 提醒改索引要在 FORK 沙箱里做，并用这批失败查询作为固定评测集回归。

## 反模式

- 只建向量索引就上线，遇到编号、人名、型号全部漏召回
- 向量查回来再在客户端过滤，导致召回不足还怪模型
- 换 embedding 模型后只重算新数据，旧向量留在原地
- 用官方 benchmark 的数字代替自己场景的实测
- 在线上库直接重建索引，没有沙箱、没有回滚路径
- 把"RRF 和加权都试过了"当结论，却不给评测集和重合度数据
